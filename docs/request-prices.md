# Request prices and the budget

This page covers what each call costs in requests and how a client paces itself against a forge's rate limit. Read it if your tool polls several repositories or shares a token with other tools.

## Request prices

Each operation's godoc publishes what the call costs on each product, under the line `Per forge:`, as one figure or as a range. A range means the operation has more than one path, such as a cached answer against a fresh read, a paginated list against a single page, or a further read that a moved repository forces. A call never spends more than its operation's published ceiling, plus the connection reads described below where the connection does not hold them yet. The test suite checks the figure for each operation on each product.

On GitLab, an owner named by digits alone costs one more request on every page of `ListRepos`, `ListMyPRs` and `ListMyIssues`. Every GitLab namespace route reads such a name as a numeric id, so the library first resolves the name to the id of the group or user that holds it.

A label write's price grows with the names it carries. Where a block says "plus one per label name", the call sends one request for each distinct name, and "plus up to one per label name" means only the names the item carries cost a request. `AddLabels` and a GitLab `RemoveLabels` send every name in one request.

On Gitea and Forgejo, `ListPRs` reads each row's reviews with one request beside its folded status, so a row costs 2 requests, and `ReadPR` adds one review read. Pass `WithReviews(false)` to keep one request per row and to drop the review read from `ReadPR`. Every pull request then answers `Approvals` and `ChangesRequested` as `CountUnknown`. On GitHub and GitLab a list or a read takes the counts in its own request or not at all, so `WithReviews(false)` saves no request there.

On GitHub, the run route serves one created filter through a result window of 1,000 runs, ending with the whole page that reaches it. A `ListRuns` walk under `WithSince` that goes past the window costs more pages than its runs fill. Each page still costs what the block states. But each time the walk narrows its created range, it reads the runs of one second twice, so it pays once more for the pages those runs fill.

## Revalidated reads

A published figure counts the requests the instance bills. On GitHub, a `304 Not Modified` answer to an authorized conditional request bills nothing, so an authorized REST read the [read cache](read-cache.md) answers from a held copy costs `0`, and so does a call answered whole that way. Those GitHub cells publish a range starting at `0`. A failed attempt still counts, and on every other product a `304` counts as one request.

## The per-product block

The same `Per forge:` block names the capability a detection can refuse the call on. It also lists every field where that product departs from the normalized contract, because it cannot supply the field, supplies another shape or spells the value differently. A field arriving exactly as the contract states has no row, which keeps the blocks short. The blocks and [SUPPORT.md](../SUPPORT.md) are generated from one table, so they cannot disagree.

## Connection reads

What a connection learns about its own instance is priced on `Capabilities.ConnectionCaps`, not on the operation that happens to need it. So every other figure is an operation's cost on a connection that already holds those facts.

On Gitea and Forgejo, that includes the page size the instance states, `max_response_items` from `GET /api/v1/settings/api`. Every page the family asks for is at most that size, so a short page is the end of a list. Two lists are the exception. The run listing continues from the total its body states. `ListRepos` under an owner continues from the `X-Total-Count` header, because that route drops the rows the caller cannot read after it pages.

An operation that needs a connection read on a connection that has not made it yet makes the read first. The request belongs to the connection, though that call's `BudgetState.LastCost` counts it. Where that read fails, the operation fails with its error and sends nothing more. Where the budget holds the read back, a list answers the empty page a deferral answers, marked `PartialRateLimited`.

Detecting the family with `families.Open` has its own cost, described in [Connecting to a forge](connecting.md#detecting-the-family).

## The budget

`Budget`, `BudgetState` and `RotationCursor` describe how a client spends requests. The client paces itself from what a response reports. On GitHub and GitLab, that figure is the whole account's quota, not this client's share of it.

- `WithMutationReserve` sets how much budget reads leave for writes. A read is deferred and marked `PartialRateLimited` while the rate-limit pool it draws on is at the reserve or below. From that pool's reset on, reads are sent again, and the next response reports the renewed budget. GitHub and GitLab name the pool each response drew on, and a route can draw on a pool of its own: on GitHub, GraphQL documents draw on another pool than REST requests, and on gitlab.com the project listings draw on a pool of 100 requests a minute. So a read is held against the pool its operation drew on last, and an operation that has had no answer yet has no pool of its own to be held against. After a deferral, `BudgetState` reports the pool that held the read. A read the call cannot mark partial fails instead with a `KindRateLimited` error carrying no status, whose `Pool`, `Remaining` and `Reset` are the held pool's. A pool whose whole limit is the reserve or less is never held, because it would defer every read after its first of each window. GitLab's pools also overlap: a request under a gitlab.com burst limit or a protected-path throttle counts against the authenticated API throttle too, though its headers name only the narrower limit. Only the packages, files and deprecated API throttles take a request apart from it. So on GitLab every read is also held against the authenticated API throttle's last figure, and each answer naming another limit takes one request off that figure until an answer reports it again. That includes the answer to an attempt that was retried and to a redirect that was followed, because each was a request GitLab counted. Forgejo reports one figure for every route, so every read is held against it.
- `ActionReads` lets the reads around one of your own writes pass the reserve, such as the precondition read before a merge and the `MergeStatus` read after it. Up to n reads under the context it returns pass the reserve, counted across goroutines, and later ones are held like any read. A read is still deferred, with no request sent, where its pool reports zero. A nested `ActionReads` keeps the outer bound, n is clamped to 1 to 20, and a read-only client ignores the mark. A forgeapi write's own reads pass the reserve without it.
- A client rotates expensive reads over a window of its own keeping. Store the `RotationCursor` it reports and pass it back with `WithRotationCursor` when you build the next client.
- `BudgetState.Remaining` counts in the instance's own units, requests on a REST endpoint and points on a GraphQL endpoint. A `304` answer still updates it from its own rate headers, except the one the [read cache](read-cache.md) cannot vouch for and sends once more.
- `BudgetState.Pools` lists each pool in name order as its own last answer reported it, with its `Remaining`, `Limit` and `Reset`. A pool whose window has renewed is left out until an answer reports it again. Each client's `PoolOf` names the pool a request's operation last drew on, for a request your observer receives, which is the pool the governor holds that operation's next read against. Forgejo reports its one figure under no name, so its pool is named `""` and `PoolOf` always answers empty on the `gitea` client.
- `BudgetRemainingUnknown` is what a product that reports nothing answers. Gitea is that product, so the reserve has no effect there.
- `DefaultBudget` publishes the defaults, including the deadline each operation runs under.

## Reading a GitHub rate limit

`github.ReadLimit` reads one GitHub answer's rate-limit facts from its status, headers and body, on any answer, a success included. `Remaining`, `Limit`, `Reset` and `Pool` are the answer's own `X-RateLimit-*` headers as sent, whatever the answer is, and `Remaining` is `BudgetRemainingUnknown` where the answer carries none. `RetryAfter` is the `Retry-After` wait as sent. `Limited` reports a 429, or a 403 carrying `Retry-After`, a remaining figure of 0 or the secondary-limit message, and `Secondary` reports a limit that carries `Retry-After` or the message. The message is read from the body's JSON `message` member alone, as "secondary rate limit" in any case, so the phrase anywhere else, or in a body that is not JSON, is no secondary limit ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit)). The `github` client's `Error` fields and the GitHub App mint read every answer the same way, so a classifier written against `ReadLimit` reads their errors alike.

GitHub sends its figures on every answer, so a secondary limit with budget left carries an `X-RateLimit-Reset` that may be most of an hour away. Wait the `Retry-After` where the answer names one. Otherwise wait until the reset only where the remaining figure is 0, and at least a minute where it is not. A secondary limit covers every pool, whatever `Pool` names. `github/githubtest.LimitCases` holds these answers as cases, REST answers and GraphQL document answers alike, each with what `ReadLimit` or the document path reads, the kind the client's `Error` answers and the `Effect` a classifier answers with: whether it holds, and which pool until when, or whether the credential was refused and the refusal is its own. The zero `Effect` holds nothing and refuses nothing.

## Counting writes

GitHub limits content creation to 80 requests a minute and 500 an hour, across the web interface and both APIs ([secondary rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#about-secondary-rate-limits)). A tool that writes for a person can count its writes against that limit with `Mutates`. Call it from a `WithAttemptObserver` or `WithRequestObserver` hook. It reports true for the REST write or GraphQL mutation a forgeapi write sends, and false for every read, the reads a write makes around it included. A GraphQL query is a `POST` on GitHub too, so the method does not tell them apart. A write is never retried, so each request it sends is one marked attempt. A read-only client marks no request.

## Refusing an attempt

An attempt observer can answer an error of its own instead of passing the request on, for example to hold a write until your own count allows it. Nothing is sent for that attempt, and it is not retried. The call fails with `CodeAttemptRefused`, and `Error.Refusal` holds your error, which `errors.As` reaches through the `*Error`. The observer sees every attempt, a retry included, so refusing a retry ends the call the same way. A failure from the transport beneath the observer, passed back through it, stays the failure it was. Because a refused attempt asked the instance nothing, every operation answers it unchanged: `ConnectionCaps` and `families.Open` never read it as an undetected family, `families.Open` asks no further family after it, and a connection reading GraphQL documents stays on documents. The `creds` sources count no refresh outcome for a refused mint or refresh and keep their standing, so the next call sends the request the observer refused. A read the governor deferred is answered unchanged by `ConnectionCaps` the same way.
